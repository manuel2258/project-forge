forge operator UI — design specification

DIRECTION “BUREAU”, DARK-FIRST · COMPANION TO forge Mockups

This document specifies what the mockups show: both themes as complete daisyUI blocks, the type and spacing scales in Tailwind terms, per-component rules, the layout and IA recommendation, an implementation order, and a note on how each planned item in §7 of the brief lands. Where a decision belongs to the engineer or the product owner rather than to this document, it is called out as Decide.

The governing idea: the operator's attention is scarce, so exactly one thing in the interface is allowed to be loud — an item that is waiting on a human. It is marked in ochre, and ochre is used for nothing else. Everything else is ruled, monochrome and quiet.

1. Layout and information architecture

1.1 Routes and measures

1.2 Navigation

Phone: a fixed three-item bottom bar — Queue, Board, Tickets — 56px tall plus safe-area inset, each item a full-height tap target. Queue carries a count badge and it is the only badge in the product. Bottom rather than top because answering is a thumb action.

Laptop: the same three as a hairline-ruled top row, left-aligned after the wordmark, with daily spend and the theme control on the right. No hamburger at any width.

Ticket, job and artifact are pushed views. They get a back affordance naming where you came from, not a tab. A ticket opened from a push notification backs out to the queue.

Answering never navigates. Every queue item is answerable in place; tapping an answer does not move you, open a page, or reorder the list. The item stays where it is and changes to its sent state.

1.3 How the queue expresses order

Oldest first, one list, no tabs and no filters — an operator must be able to reach the end and know they are done. Three devices carry the ordering: the waiting figure on every item (the sort key, set large and right-aligned so the age of the whole queue reads down one edge); a counter in the header (4 left · in order); and a terminal End of queue block that is phrased as a completion. Non-blocking questions sit below the last actionable item under a heading that says they are not waiting on you — present, never hidden, never competing.

2. The three axes

This is the central problem in the brief and everything else follows from it. The three axes are given three different forms, not three colours of the same badge — form survives colour-blindness, greyscale and a glance.

Axis Form Rules

No border and no padding — a border in this system means the thing is tappable, so an identifier never has one.Glyph: ▸ job state (runs a job on entry, info hue) · ● human state with outgoing transitions (primary hue) · ■ terminal (muted). Never coloured by status. Never abbreviated.
2 · ticket statusFilled flag, placed beside the state chip.Rendered only when not active. stuck = filled accent with its age inside (STUCK 19h). done = outlined success. Never replaces the state and never appears as a board column.
3 · job outcomeBare mono text at type scale, coloured.The declared outcome is the largest: 30px on the job page, 12.5px in a jobs table column of its own. The engine outcome is demoted to smaller mono beside it. Job status is plain mono. Nothing on any axis is boxed.

Outcome colour mapping. converged and any declared success → success. did_not_converge and budget_exhausted → warning. error and declared failures the agent names (tests_failed, plan_invalid when it blocks) → error. did_not_converge is deliberately not red: it is the agent honestly reporting it could not finish.

Declared outcomes are project-defined strings. Do not hard-code the list. Map by three buckets the workflow declares — success, non-completion, failure — and fall back to neutral for an unrecognised value. Decide: whether the workflow grammar can carry that bucket per allowed outcome, or whether the UI must infer it.

3. Type and spacing

3.1 Faces

Instrument Sans for everything that is language, JetBrains Mono for everything that is an identifier. Both are OFL and self-hostable, which is the binding constraint — no CDN, possibly no egress. Ship subsetted woff2 (latin, weights 400/500/600 and 400/500/700) in assets/fonts/ with a local @font-face block and font-display: swap; roughly 90 KB total.

Instrument Sans was chosen over the obvious UI sans for two reasons: it has a narrow, slightly condensed lower case that holds a 20px decision sentence on a 390px screen without wrapping to four lines, and its figures are unfussy enough to sit beside mono without the page reading as two products. Decide: if self-hosting any webfont is unwelcome, the system stack degrades acceptably — the design depends on the sans/mono distinction, not on these two faces.

3.3 When monospace applies

Mono is for things the system named: workflow states, ticket statuses, job statuses and outcomes, artifact names and version numbers, branches, commit shas, session ids, environments, money, counts, durations and ages, transition buttons (→ planning), and micro labels.

Mono is never for things a person wrote or reads as language: ticket titles, question text, option labels, anchor quotations, explanatory sentences, empty-state copy, button labels that are verbs (Approve v3, Retry now). This is the rule that fixes “monospace is the dominant texture” — the volume of mono drops by roughly half while every identifier still looks like one.

3.4 Spacing and targets

Base unit 4px. Page gutter px-5 phone / px-6–px-[30px] laptop. Queue item py-[18px], internal stack gap gap-[11px]. Timeline step gap pb-[26px] laptop / pb-5 phone. The old py-20 page padding goes; vertical space on a phone is the scarcest resource in the product after attention. Every tap target is at least 46px tall, answer buttons 48px, and btn-sm does not appear on any operator page. Separation is a 1px rule, not a shadow — --depth: 0.

4. Colour — both themes

Dark is the design target and light is derived from it. Hue is constant across both (300 neutrals, 290 primary, 62 accent, 240 info, 150 success, 22 error); only lightness and chroma move. Body text is ≥ 7:1 against its own base in both themes, muted text ≥ 4.5:1. The accent is deliberately identical in both themes with dark content text, so the one loud mark in the product does not shift meaning when the theme does.

4.3 Colour discipline

Accent (ochre) means one thing: a human is being waited on. The queue mark on a blocking or stuck item, the STUCK flag, the ticket's current-step dot, the board's left rule, the “waiting on you” count, the usage meter fill and the window gauge. Nothing else may use it — its value is entirely in its scarcity.

Primary (indigo) is links, human states, and decisions that advance state or spend money. Info (blue) is the job-state glyph and harness tool calls, nothing else. Success is approval and the end of the queue. Error is reserved: engine errors, declared failures, and failed sends.

Two surfaces per theme at most: base-100 for pages, base-200 for the one row that is in a changed state (answered, current attempt). Structure is rules, not cards — border-base-300 at full strength for section rules, border-base-300/60 for rows within a section.

5. Components

The affordance rule, which governs every component below: a border means you can tap it. Identifiers — states, statuses, outcomes, branches, commits — are plain mono text with no box. Actions are boxed: a 52px row with the label left and a › right, which sends on tap. A filled button appears only where the operator has typed something to commit. A filled uppercase tag is a flag, never a control.

5.1 Queue item — one shape, N kinds

Every kind is the same five-part row, so the list never becomes soup as kinds are added: (a) mark + kind label + waiting figure; (b) the decision sentence at text-xl; (c) optional context, one or two lines of prose, including the anchor quotation; (d) the answer affordance; (e) a mono footer of identifiers. Separation between items is a top rule, not a card.

Three marks carry all kinds. Filled accent diamond — a job is held or the ticket is stuck (blocking question, stuck, and later experiment requests that hold a job). Hollow primary square — a decision that advances state or spends money (approval, promotion decision). Hollow success circle — routine (review ready, analysis proposal). The kind is named in words beside the mark, so eight kinds need eight labels but only three marks.

Kind Answer affordance Notes
Blocking questionStacked 48px option buttons, default filled; free-text field last.Anchor quotation always shown with the artifact name and version. Free text is a peer of the options and is labelled ALWAYS OPEN, never hidden behind a link.
ApprovalApprove vN / Reject, plus optional comment.The version number is inside the button label. Sentence states the transition and the artifact; one line states that approval pins that exact version.
StuckOne mono button per available transition.Sentence states why it is stuck (cap, no match, ceiling). Footer carries the state chip — the ticket is still in it.
Review readyTransition buttons.Quietest kind. A human state with no outgoing transitions never appears in the queue at all — it is terminal, nothing is waiting.
Non-blocking questionNone inline; links to the document.Digest block below the last actionable item, under Not waiting on you. One line each. Never pushed to the phone.

5.2 Ticket page

Header: project#number in mono, title at text-3xl, then the state chip, the status flag if any, and a plain-language clause for why it is waiting. Cost is not in the header — it is the first block of the rail, where it can carry its ceiling.

Hoisted decision: if the ticket has an answerable action, it appears once, directly under the header, in an accent-bordered block. Everything below it is reference. This is the only place on the page where accent appears besides the current-step dot.

Timeline: one step per workflow state, in the workflow's own order, walked from the initial state — the same walk the board uses for columns. Each step carries its dot and rail, the state name in mono, the topology glyph, a jobs table (attempt, declared outcome, turns, cost), artifact chips written in that state, and a right-aligned summary (3 jobs · $1.15). States not yet reached are drawn at 50% so the operator can see where the ticket is going; the rail stops at a terminal state. Stuck is drawn on the current step — accent dot plus flag — never as a step of its own.

Rail: usage meter and window capacity, facts (branch, base, workflow commit, admitted), artifact index with approval state per version, and the last four events with a link to all of them. The full event timeline moves off the ticket page to its own disclosure — 200 rows of mono is a post-mortem tool, not a page header.

5.3 Job page

Declared outcome is the page headline at text-3xl mono in its outcome colour, with the engine outcome as a chip beside it and a caption naming which is which. Turns, cost and duration are three figures in a row, turns always against its budget. The pinned manifest is the rail: branch, workflow commit, environment, budget, session, then each input artifact at its exact version. When an input has been superseded the row reads v2 exists in warning and a sentence below states the platform did not re-run on its own. Allowed outcomes are listed with the taken one marked. The harness stream is headed COMPLETE · N ENTRIES, newest first, 50 per page, no tailing and no autoscroll.

5.4 Board

Columns in workflow-walk order, each headed by the state name, its topology glyph and its count. Columns cap at four rows and then say how many remain — a column that scrolls independently hides its own count and breaks the board as a shape. Cards are two lines: number in mono, title in sans; a ticket waiting on a human gains an accent left rule and a mono age. The human-state column gets a tinted ground. Terminal columns are dimmed. The header carries three figures only: open count, N waiting on you in accent, daily spend. On phone the columns become sections in the same order, collapsed except any section containing work that waits on you.

5.5 Artifacts

The unit is a chip: name, version, approval state. There is no chip without a version and the word “latest” appears nowhere in the product. States: ✓ approved (success), ◇ unapproved (warning), no marker where approval does not apply. Opening a chip discloses a version strip — v1 agent → v2 you, edited → v3 agent — which is both provenance and the place multi-user attribution lands later. A presentation is drawn with a dashed border and VIEW ONLY and has no approval slot at all, so it cannot be misread as approvable.

5.6 Capacity and usage

Cost is modelled as consumed capacity, not money. One unit is one percent of a five-hour window, and quantities are stated in windows to two significant figures (1.4 windows). This gives one unit that stays true when a ticket's work spans four windows and a week, which a percentage cannot.

The model has two objects and they are never drawn the same way. Usage is absolute and never resets: a job's usage, a timeline step's sum, a ticket's total against its allowance. Capacity is a live shared pool that refills: the current five-hour window and the week, each with a reset time. A ticket allowance stays absolute — a cap expressed as a share of a refilling pool would mean something different on Monday than on Friday.

Drawing. The window is a twenty-tick gauge (one tick per five percent) with a mono reset countdown, because you are consuming it rather than progressing through it; it compresses to ten ticks in the top bar and replaces the daily-spend readout. The week is a thin plain bar beneath it and becomes the headline only when it is the binding ceiling. Ticket usage is a figure plus a 5px meter against its allowance, filled accent. A job states its usage, its turn budget, and — only when a reset interrupted it — which windows it drew from and how long it was paused.

Three exhaustions, three treatments. A job turn budget running out is the engine's business: it appears as the outcome budget_exhausted and nowhere else. A ticket allowance running out needs a human, so it sticks the ticket, enters the queue and is drawn in accent. Window or weekly capacity running out is resolved by time: it is drawn neutral as PAUSED · CAPACITY 1h 12m on the board and the ticket, never in accent, and never in the queue. That last rule is load-bearing — a paused ticket in the inbox trains the operator to open items they cannot act on, which is the failure the whole thesis is written against.

Decide. (a) Whether the provider reports a real window boundary and reset time; a wrong countdown is worse than none. (b) Whether a job that meets a window edge hibernates and resumes or fails and retries — the PAUSED treatment assumes the former and is where §7's hibernation work surfaces. (c) Whether dollars survive as a secondary figure on the job page for reconciliation. The recommendation is that they leave every operator surface: a number the operator cannot act on is noise, and capacity is a number they can act on.

5.7 Message state

Four states, one row shape, always attached to the item acted on — never a toast, because a toast that disappears is precisely the failure the vision calls impossible by construction.

Queued/sending — spinner, “saved on this device”, Undo. Retrying — accent diamond, attempt count, next-attempt countdown, Retry now. Failed — error dot, “gave up after 5 tries”, “still saved · tap to try again”. The answer is never discarded. Confirmed — success tick, the time, and the consequence (job resumed), so the row closes the loop rather than just the request.

The item does not disappear on tap and does not reorder. An offline banner states how many answers are waiting to send. The two generic reconnect banners are replaced by one that names the consequence for the operator's own work. Decide: offline compose needs a client-side outbox that survives LiveView DOM patching and page reload — an idempotency key per answer and a service-worker-backed store. That is engineering work this document assumes but does not specify.

5.8 Empty states

The empty queue is what a well-running system looks like, so it is drawn as a completion: a success micro-label End of queue, a sentence, and one line of evidence that work happened without you (14 jobs ran today and none of them needed you). The same block terminates a non-empty queue. Every other empty state names what would fill it rather than announcing absence — an empty board column says nothing in this state; a ticket with no artifacts yet says the first job writes plan.md.

6. Implementation order

Ordered by impact per unit of work. Each step is shippable on its own and none of them requires the next.

# Step Why here

Where this design could paint you into a corner. Two places. First, capping board columns at four rows assumes the board stays a shape rather than becoming a workspace; if tickets ever need to be dragged between states, the cap has to go and the column becomes a scroller. Second, the queue's refusal of tabs and filters is correct at one operator and 4 items, and will need revisiting — not reversing — if multi-user arrives and the list carries items addressed to other people. The honest answer then is per-person queues, not filters.

8. Decisions needed

  1. Whether /tickets is worth the query work now, or is deferred and the phone bar drops to two items.
  2. Whether the workflow grammar can declare a bucket (success / non-completion / failure) per allowed outcome, so declared-outcome colour is not inferred from string matching.
  3. Whether the engine can report “an input artifact of this job has been superseded”, which the stale-input notice needs.
  4. Whether self-hosted webfonts are acceptable at all; if not, the system stack is a supported fallback.
  5. The retry policy the message-state copy states literally — five attempts with backoff is assumed here and should match what is implemented.
  6. The three capacity questions in §5.6: provider-reported window boundaries, hibernate-or-retry at a window edge, and whether dollars survive anywhere in the operator UI.
